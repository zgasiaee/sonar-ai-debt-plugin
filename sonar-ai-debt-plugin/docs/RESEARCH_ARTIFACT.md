## 1. Artifact synopsis

AI Debt Metrics is a research-oriented SonarQube Server plugin for examining technical
and cognitive debt signals in Python code associated with AI-assisted development. It
accepts either a single Python task or a multi-file Python project; both are processed
through the same project-analysis pipeline.

The software publishes:

- four technical signals: AISD, CII, CDI, and HTS;
- four cognitive signals: CSD, RLR, SII, and EGR;
- the aggregate TDSI, CogDI, and ADSI indices;
- applicability and analysis-scope diagnostics;
- source-located evidence and rule-specific remediation guidance;
- SonarQube issues for source-located findings; and
- a project-level interactive dashboard.

The artifact does **not** classify whether code was generated by AI. It measures
predefined debt signals in a codebase whose provenance is supplied by the study design.
The presence of a signal is not, by itself, proof of AI authorship or a runtime defect.

## 2. Claims supported by the artifact

The artifact is designed to support the following software claims:

1. The analyzer can parse supported Python main-source files and calculate all eight
   component metrics using one project-level workflow.
2. It can ingest source-located SpecDetect4AI findings as the exclusive AISD smell source.
3. It publishes raw measures, normalized results, applicability information, diagnostics,
   evidence, and aggregate indices to SonarQube.
4. Automated regression tests exercise every component metric using compact inline
   inputs that are not distributed as user-facing example projects.
5. The same workflow can be reused on another Python repository by changing only the
   scanner configuration and SpecDetect4AI input path.

The artifact does not independently establish construct validity, causal attribution,
or a Human-versus-AI difference. Those claims require the empirical protocol described
in [`VALIDATION.md`](VALIDATION.md).

## 4. Processing workflow

```text
Python project
    |
    +--> SpecDetect4AI ----------------------> specDetect4ai_results.json
    |                                                |
    +--> SonarScanner --> AI Debt sensor ------------+
                              |
                              +--> Python AST and project analysis
                              +--> component metrics and diagnostics
                              +--> TDSI, CogDI, and ADSI
                              +--> source-located SonarQube issues
                              +--> project dashboard and Web API measures
```

AISD is not silently approximated when the external report is unavailable. It is marked
not applicable, and aggregation renormalizes the remaining applicable weights. The other
metrics are calculated by the Java analyzer from the Python source scanned by SonarQube.

## 7. Installation

All commands below assume a POSIX shell. Windows users can run equivalent commands in
PowerShell and activate the virtual environment with `.venv\Scripts\Activate.ps1`.

### 7.1 Acquire and identify the artifact

```bash
git clone https://github.com/zgasiaee/sonar-ai-debt-plugin.git
cd sonar-ai-debt-plugin/sonar-ai-debt-plugin
git rev-parse HEAD
```

Record the returned commit in the metadata table. Do not evaluate an unrecorded moving
branch.

### 7.2 Build and verify the plugin

```bash
java -version
mvn -version
mvn clean verify
```

Successful completion creates:

```text
target/sonar-ai-debt-plugin-0.1.0-SNAPSHOT.jar
```

At the current revision, the Maven verification suite executes 45 tests with zero failures,
errors, or skipped tests. The threshold-calibration utilities add four Python unit tests.
The number may increase in later revisions; no test should fail.

Run the calibration-tool tests from the plugin directory with:

```bash
python3 -m unittest discover -s research/thresholds -p 'test_*.py' -v
```

Optional checksum:

```bash
shasum -a 256 target/sonar-ai-debt-plugin-0.1.0-SNAPSHOT.jar
```

Use `sha256sum` instead of `shasum -a 256` on systems that provide GNU coreutils.

### 7.3 Install SpecDetect4AI dependencies

From the artifact root:

```bash
cd SpecDetect4AI-B903
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python specDetect4ai.py --list-rules
deactivate
```

The recorded snapshot pins:

```text
lark==1.2.2
lark_parser==0.12.0
```

The final command should print the supported rule catalogue, including R1–R24 and the
R11bis detector.

### 7.4 Start an evaluation SonarQube instance

The embedded database is appropriate only for this local evaluation. It must not be used
as a production or long-term research database.

```bash
docker run -d \
  --name sonarqube \
  -p 9000:9000 \
  -e SONAR_ES_BOOTSTRAP_CHECKS_DISABLE=true \
  -v sonarqube_data:/opt/sonarqube/data \
  -v sonarqube_extensions:/opt/sonarqube/extensions \
  -v sonarqube_logs:/opt/sonarqube/logs \
  sonarqube:community
```

Wait until this endpoint reports `"status":"UP"`:

```bash
curl --fail http://localhost:9000/api/system/status
```

If a container named `sonarqube` already exists, inspect it first:

```bash
docker ps -a --filter name=sonarqube
```

Start that container with `docker start sonarqube`, or choose another container name and
update subsequent commands. Do not delete an existing container unless its data is
disposable.

### 7.5 Install the plugin JAR

From `sonar-ai-debt-plugin/`:

```bash
docker cp \
  target/sonar-ai-debt-plugin-0.1.0-SNAPSHOT.jar \
  sonarqube:/opt/sonarqube/extensions/plugins/sonar-ai-debt-plugin-0.1.0-SNAPSHOT.jar

docker restart sonarqube
```

Wait for the server to return to `UP`. To confirm that only the intended JAR is installed:

```bash
docker exec sonarqube \
  ls -l /opt/sonarqube/extensions/plugins
```

When replacing the plugin, overwrite or remove the previous JAR and restart the server.
Never leave two versions of the same plugin in the extensions directory.

### 7.6 Create a SonarQube project and token

1. Open `http://localhost:9000`.
2. Sign in. A new local evaluation instance initially uses `admin` / `admin` and requires
   changing the password.
3. Create a local project with a unique key for the Python repository under analysis.
4. Generate a project-analysis token during project setup, or open the user menu and
   navigate to **My Account → Security**.
5. Copy the token when it is displayed; SonarQube does not display it again.

Export it without writing it to a tracked file:

```bash
export SONAR_TOKEN='<TOKEN_VALUE>'
```

Do not commit a token to `sonar-project.properties`, shell history, source code, or an
artifact archive.

## 8. End-to-end execution on a Python project

### 8.1 Create the scanner configuration

Create `sonar-project.properties` in the root of the Python repository to be analyzed:

```properties
sonar.projectKey=<UNIQUE_PROJECT_KEY>
sonar.projectName=<PROJECT_NAME>
sonar.projectVersion=<IMMUTABLE_RUN_OR_RELEASE_ID>
sonar.sources=.
sonar.sourceEncoding=UTF-8
sonar.python.version=<TARGET_PYTHON_VERSION>
sonar.host.url=http://localhost:9000
sonar.aidebt.specdetect.reportPath=specDetect4ai_results.json
```

The project key must match the key created in SonarQube.
The path in `sonar.aidebt.specdetect.reportPath` is relative to the scanner base directory.

### 8.2 Generate AISD input

From the target Python repository:

```bash
/absolute/path/to/SpecDetect4AI-B903/.venv/bin/python \
  /absolute/path/to/SpecDetect4AI-B903/specDetect4ai.py \
  --input-dir . \
  --all \
  --summary \
  --output-file specDetect4ai_results.json
```

Confirm that the report exists and is non-empty:

```bash
test -s specDetect4ai_results.json
```

The JSON object groups messages by Python file and rule identifier. Keep the report in the
scanner base directory unless `sonar.aidebt.specdetect.reportPath` is changed.

### 8.3 Run SonarScanner

From the same target-project directory:

```bash
sonar-scanner \
  -Dsonar.host.url=http://localhost:9000 \
  -Dsonar.token="$SONAR_TOKEN"
```

A successful run ends with `EXECUTION SUCCESS`. The scanner uploads source analysis and
the AI Debt measures; SonarQube then processes the background task. If needed, open
**Project Settings → Background Tasks** and wait until the task is successful.

## 9. Produced outputs

### 9.1 Dashboard

Open the analyzed project and select:

```text
Extensions → AI Debt
```

The overview reports:

- ADSI, TDSI, and CogDI;
- metric applicability coverage;
- the technical and cognitive component signals;
- each metric's active contribution;
- estimated remediation workload; and
- links to the metric-specific analysis pages.

Each metric page reports interpretable inputs, thresholds where applicable, result
severity, compact source-located evidence, and the active weighted calculations needed to
reconstruct the aggregate indices.

### 9.2 SonarQube issues

Open the project's **Issues** page and filter by the **AI Debt** repository. AISD
SpecDetect4AI issues include:

- stable rule identifier;
- rule title and severity;
- file and line;
- detector evidence;
- rationale; and
- recommendation specialized to the detected API and source expression.

These are review candidates. Category-2 and category-3 SpecDetect4AI rules can depend on
implicit configuration or runtime behavior that static analysis cannot prove.

### 9.3 Measures through the Web API

The primary numerical results can be exported without scraping the dashboard:

```bash
export PROJECT_KEY='<UNIQUE_PROJECT_KEY>'

curl --fail --user "$SONAR_TOKEN:" \
  "http://localhost:9000/api/measures/component?component=${PROJECT_KEY}&metricKeys=aidebt_aisd,aidebt_aisd_score,aidebt_cii,aidebt_cdi,aidebt_cdi_score,aidebt_hts,aidebt_csd,aidebt_rlr,aidebt_sii,aidebt_egr,aidebt_tdsi,aidebt_cogdi,aidebt_adsi,aidebt_metric_coverage,aidebt_files,aidebt_logical_lines,aidebt_blocks"
```

Save the response for a research run:

```bash
mkdir -p artifact-results

curl --fail --user "$SONAR_TOKEN:" \
  "http://localhost:9000/api/measures/component?component=${PROJECT_KEY}&metricKeys=aidebt_aisd,aidebt_aisd_score,aidebt_cii,aidebt_cdi,aidebt_cdi_score,aidebt_hts,aidebt_csd,aidebt_rlr,aidebt_sii,aidebt_egr,aidebt_tdsi,aidebt_cogdi,aidebt_adsi,aidebt_metric_coverage,aidebt_files,aidebt_logical_lines,aidebt_blocks" \
  --output artifact-results/measures.json
```

The SonarQube API also exposes analysis history. Record the server version, plugin commit,
configuration, detector revision, scanner version, and analysis timestamp with every
export.

## 10. Expected validation outcome

`mvn clean verify` is the authoritative plugin-level validation command.
`ProjectAnalyzerTest.allMetricsRegressionInputProducesANonZeroSignalForEveryMetric`
uses compact inline Python inputs to verify that all eight component metrics can become
applicable and produce non-zero signals. `GoldenMetricTest` contains smaller
hand-checkable calculations, and `SpecDetectReportParserTest` verifies source-located
AISD report ingestion.

For an end-to-end scan of a target repository:

- the analyzed file and logical-line counts must match the configured Python source scope;
- the SpecDetect4AI report must be generated from the same source revision;
- metrics whose required denominator is absent must be reported as not applicable;
- AISD must be not applicable when its external report is absent;
- dashboard values must agree with the Measures API response; and
- published issues must point to files and lines in the scanned revision.

Metric values are project-dependent; this artifact does not prescribe expected scores for
an arbitrary repository.

## 11. Reusing the artifact on another Python project

### 11.1 Add project configuration

Create `sonar-project.properties` in the target Python repository:

```properties
sonar.projectKey=<UNIQUE_PROJECT_KEY>
sonar.projectName=<PROJECT_NAME>
sonar.projectVersion=<IMMUTABLE_RUN_OR_RELEASE_ID>
sonar.sources=.
sonar.sourceEncoding=UTF-8
sonar.python.version=<TARGET_PYTHON_VERSION>
sonar.host.url=http://localhost:9000

sonar.aidebt.enabled=true
sonar.aidebt.specdetect.reportPath=specDetect4ai_results.json
sonar.aidebt.tdsi.weights=0.25,0.25,0.25,0.25
sonar.aidebt.cogdi.weights=0.25,0.25,0.25,0.25
sonar.aidebt.index.weights=0.5,0.5
sonar.aidebt.csd.similarityThreshold=0.45
sonar.aidebt.csd.componentWeights=0.333333333333,0.333333333333,0.333333333334
sonar.aidebt.rlr.syntaxSimilarityThreshold=0.85
sonar.aidebt.rlr.behaviorSimilarityThreshold=0.90
sonar.aidebt.rlr.behaviorComponentWeights=0.333333333333,0.333333333333,0.333333333334
sonar.aidebt.sii.conceptSimilarityThreshold=0.75
sonar.aidebt.sii.contextSimilarityThreshold=0.75
sonar.aidebt.sii.nameSimilarityCeiling=0.40
sonar.aidebt.egr.complexityThreshold=5
sonar.aidebt.egr.nestingThreshold=3
sonar.aidebt.egr.mixedFlowComplexityThreshold=4
sonar.aidebt.egr.mixedFlowKindThreshold=2
sonar.aidebt.pairBudget=1000000
```

Exclude generated, vendored, test, or virtual-environment code according to a
preregistered corpus policy. For example:

```properties
sonar.exclusions=**/.venv/**,**/venv/**,**/build/**,**/dist/**,**/generated/**
```

Apply the same exclusion policy to all compared Human and AI conditions.

### 11.2 Generate the detector report and scan

From the target project root:

```bash
/absolute/path/to/SpecDetect4AI-B903/.venv/bin/python \
  /absolute/path/to/SpecDetect4AI-B903/specDetect4ai.py \
  --input-dir . \
  --all \
  --summary \
  --output-file specDetect4ai_results.json

sonar-scanner \
  -Dsonar.host.url=http://localhost:9000 \
  -Dsonar.token="$SONAR_TOKEN"
```

Task-sized and project-sized inputs need no different analyzer mode. The analysis scope is
the set of supported main-source files selected by SonarScanner.

### 11.3 Configuration discipline for comparative studies

For a reproducible Human-versus-AI study:

1. freeze the plugin commit, SonarQube image, scanner, SpecDetect4AI revision, exclusions,
   weights, and thresholds before confirmatory analysis;
2. use identical configuration for paired Human and AI implementations;
3. preserve task/project pairing in exported metadata;
4. retain raw component measures and applicability, not only ADSI;
5. never replace not-applicable values with zero;
6. archive scan logs, detector reports, API exports, and configuration files; and
7. keep source provenance labels outside the metric engine.

The default weights and thresholds implement the frozen `consensus-adjudicated-v1`
profile in [`../profiles/consensus-adjudicated-v1.properties`](../profiles/consensus-adjudicated-v1.properties).
Alternative profiles belong to a separately versioned sensitivity analysis. See
[`THRESHOLD_CALIBRATION.md`](THRESHOLD_CALIBRATION.md) and [`VALIDATION.md`](VALIDATION.md).

## 12. Optional exploratory weight calibration

The repository includes a CRITIC-based exploratory script:

```bash
python3 research/calibrate_weights.py \
  --tdsi <TDSI_COMPONENT_CSV> \
  --cogdi <COGDI_COMPONENT_CSV> \
  --bootstrap 1000 \
  --output research/output/weights.json
```

This script is not required to build or run the plugin. Do not optimize weights against
the Human/AI provenance label and then use the resulting index as evidence that the two
groups differ. Any non-default weights must be recorded in `sonar-project.properties`
and reported as a sensitivity analysis.

## 13. Troubleshooting

| Symptom | Likely cause | Corrective action |
|---|---|---|
| Docker reports that `/sonarqube` is already in use | A container with that name already exists | Inspect with `docker ps -a`; start it or choose a different name |
| SonarQube never reaches `UP` | Insufficient Docker memory or host limits | Inspect `docker logs sonarqube`; increase allocated resources |
| The AI Debt page is absent | JAR missing, duplicate plugin versions, or server not restarted | Inspect `extensions/plugins`, keep one JAR, and restart |
| Scanner returns 401 | Missing, expired, or unauthorized token | Generate a project-analysis token and export `SONAR_TOKEN` |
| Scanner reports zero supported files | `sonar.sources`/exclusions are wrong or files are not `.py` main sources | Correct the project base directory and source selection |
| AISD is N/A | SpecDetect4AI report is missing or the configured relative path is wrong | Generate the JSON report before scanning and verify its path |
| AISD is zero | The report exists but contains no supported findings | Inspect JSON rule IDs and run SpecDetect4AI with `--all --summary` |
| Evidence says source unavailable | Report path/line does not match the scanned revision | Regenerate the report from the exact source revision immediately before scanning |
| Some metrics are N/A | Their denominator or required construct is absent | Treat as not applicable and inspect applicability diagnostics |
| Old values remain after a code change | The project was not rescanned or background processing is pending | Rerun the scanner and verify the background task |
| Maven cannot resolve dependencies | Network/proxy or local repository issue | Configure Maven proxy access and rerun `mvn clean verify` |

For scanner diagnostics:

```bash
sonar-scanner -X \
  -Dsonar.host.url=http://localhost:9000 \
  -Dsonar.token="$SONAR_TOKEN"
```

Do not publish debug logs without checking them for paths, tokens, or confidential source
metadata.

## 15. Data, security, and ethical considerations

- Source code and detector reports can contain confidential paths, identifiers, and code
  fragments. Store and share them according to the source repository's license and study
  consent conditions.
- Never place credentials in analyzed source or the artifact. If a secret detector finds
  a real credential, revoke it before archiving any output.
- SonarQube's embedded database is for evaluation only.
- The dashboard reports standardized remediation effort, not observed developer elapsed time.
  It sums deduplicated repair actions using the fixed SonarSource-aligned easy, medium, and
  major costs. Archive the `aidebt_effort_model` measure with every reported run.
- A finding should be reviewed in context before remediation or publication.
- The tool must not be used to infer developer identity, competence, or AI authorship from
  code signals alone.
